# Nativeproof Shared Contract (v1)

This directory is the integration contract between the frontend, the backend, and QA.
Where it differs from `docs/07_API_SPEC.md`, this contract wins; every difference is
recorded in `docs/14_DECISIONS.md`.

## 1. Source-of-truth chain

```text
backend/app/schemas/*.py           Pydantic request/response models
backend/app/api/routes/*.py        paths, methods, status codes, parameters
        |  cd backend && uv run python -m scripts.export_openapi
        v
contracts/openapi.json             generated; never edit by hand
        |  cd frontend && npm run gen:api
        v
frontend/src/lib/api/schema.d.ts   generated TypeScript types

contracts/fixtures/*.json          generated by: uv run python -m scripts.build_contract_fixtures
```

`backend/tests/contract/` fails when `openapi.json` is stale or a fixture violates its schema.

## 2. Ownership and change process

| Path | Owner |
|---|---|
| `backend/app/schemas/`, route signatures in `backend/app/api/routes/`, `contracts/` | Integration owner (main session) |
| Route handler bodies and the rest of `backend/` | Backend workstream |
| `frontend/` | Frontend workstream |
| `tests/integration/`, `e2e/` | QA workstream |

To change the contract, send the integration owner the exact change and the reason. After
approval the owner edits the schemas, regenerates `openapi.json` and the fixtures, and commits
to `main`. Workstreams then merge `main`. Never work around a contract problem locally.

## 3. Conventions

- Base URL: `{API_BASE}/api/v1`. Health checks live at `/health` and `/ready` (no prefix).
- IDs are UUIDs. Timestamps are ISO 8601 UTC.
- Pagination: `limit` (1–100, default 20) and `offset`. Responses: `{items, limit, offset, total}`.
- PATCH: omitted fields stay unchanged.
- Unknown request fields are rejected with `422 VALIDATION_ERROR`.
- Every response carries `X-Request-ID`. The backend echoes the incoming header or generates one.
- Resources owned by another user return `404 NOT_FOUND`, never `403`, so their existence is not revealed.
- When a body references another resource (a run, adaptation, or content version):
  - another user's resource → `404 NOT_FOUND`
  - the caller's resource in a different project or campaign → `409 CONFLICT`
  - the wrong run type, or a run that is not `completed`/`partial` → `409 CONFLICT`

  `details[].field` names the offending field in each case.
- `details[].field` is a dotted path without the `body`/`query`/`path` prefix, with list indexes as numbers
  (`original_content.reference_terms.2`). It is null only when no field applies.
- CORS: allow the origins in `FRONTEND_ORIGINS` and the methods `GET, POST, PUT, PATCH, DELETE, OPTIONS` (`PUT` is Brand Memory's full replacement). Allow the
  request headers `Authorization, Content-Type, X-Request-ID`, and expose `X-Request-ID, Content-Disposition`.
  No cookies: authentication is the bearer token only.
- `/ready` returns `503` with the `Readiness` body when `status` is `not_ready`. `ready` and `degraded` return `200`.

### Errors

Every error uses `{"error": {"code", "message", "details": [{"field", "message"}], "request_id"}}`.
FastAPI validation errors are mapped into this envelope. Clients never see stack traces or provider details.

| Code | HTTP | Meaning |
|---|---:|---|
| `VALIDATION_ERROR` | 422 | Invalid body or parameters |
| `UNAUTHENTICATED` | 401 | Missing, invalid, or expired token |
| `FORBIDDEN` | 403 | Authenticated, but the action is not permitted |
| `NOT_FOUND` | 404 | Missing, or owned by someone else |
| `CONFLICT` | 409 | State conflict: archived project, content edit on a demo campaign, candidate from another source version |
| `RATE_LIMITED` | 429 | Too many active runs (`MAX_ACTIVE_RUNS_PER_USER`) |
| `PROVIDER_NOT_CONFIGURED` | 503 | A live run needs a provider whose credentials are not configured |
| `UNSUPPORTED_CAPABILITY` | 501 | The verified Qloo workflows cannot answer the request |
| `PROVIDER_ERROR` | 502 | Provider failed (normally reported in `Run.error`) |
| `PROVIDER_TIMEOUT` | 504 | Provider timed out (normally reported in `Run.error`) |
| `RUN_FAILED` | 500 | Workflow failed, e.g. model output still invalid after the bounded repair (`Run.error`) |
| `RUN_INTERRUPTED` | — | Server restarted during the run; retryable (`Run.error` only) |
| `INTERNAL_ERROR` | 500 | Unexpected error |

## 4. Authentication

- **`AUTH_MODE=supabase`.** The frontend signs in with Supabase Auth: email and password, or
  anonymous sign-in for "Try the demo". It then sends `Authorization: Bearer <access_token>`.
  The backend verifies the token against the JWKS at `{SUPABASE_URL}/auth/v1/.well-known/jwks.json`,
  falling back to HS256 with `SUPABASE_JWT_SECRET` only when that is set. It checks `exp`,
  `aud = authenticated`, and `iss = {SUPABASE_URL}/auth/v1`. The user id comes from `sub`.
- **`AUTH_MODE=dev`** is for local development and tests only. The backend refuses to start in
  this mode when `APP_ENV=production`. A token `dev-<label>` maps to user id
  `uuid5(NAMESPACE_URL, "nativeproof-dev:<label>")`. The frontend's dev mode sends `Bearer dev-local`.
  Different labels act as different users in isolation tests.
- Every resource belongs to a project, and `project.owner_id` is the caller's user id.
  Ownership is enforced in the backend; Row Level Security is defense in depth.

## 5. Live mode and demo mode

- Mode belongs to the **project** and is fixed at creation. `POST /projects` creates a live
  project. `POST /projects/demo` creates a demo project seeded with the fixture brand (Northstar),
  campaign (Autumn Launch Campaign), and market (Japan).
- **Demo projects** run the real pipeline (validation, aggregation, scoring, persistence) through
  a fixture Qloo adapter and a fixture LLM provider. Results are deterministic. Evidence has `is_live_data: false`,
  with `retrieval_mode: "fixture"` for provider data and `"generated"` for calculations and interpretations.
  Fixture records carry `provenance.fixture_origin`. `StepTrace.provider` is `"fixture"` or `"nativeproof"`.
  `Run.mode` is `"demo"`. Demo runs never call an external provider.
- **Demo scope.** A demo project is one curated scenario: the seeded brand, campaign, and study
  (`POST /projects/demo` seeds all three). The fixtures only describe that scenario, so in demo projects:
  - These return `409 CONFLICT`: creating campaigns or studies, editing the brand, editing campaign content,
    and starting a run for any market other than the seeded one (JP).
  - Discovery accepts any reference terms. Terms without a fixture come back `unresolved` with the limitation
    "No demo fixture for this term."
  - Rehearsal uses the fixture reactions for the seeded study. `response_count` is honored up to the number of
    fixture reactions; `generated_responses` reports the true count, and a limitation says when fewer were available.
  - Adaptation honors `variant_count` up to the fixture variants (3).
  - Evaluation: fixture scores exist only for the seeded original and the fixture variants. A user-edited
    revision gets null scores, which yields R0 `inconclusive` with the limitation "Demo fixtures cannot assess edited text."
- **Exports** of a demo-mode report start with `DEMO DATA — fixture results, not live research` and keep every
  evidence label and retrieval badge.
- **Live projects** call Qloo and Nebius (OpenRouter only as a recorded, explicitly enabled
  fallback). If a provider is not configured, starting the run returns `503 PROVIDER_NOT_CONFIGURED`.
  A provider failure produces a `failed` or `partial` run with `Run.error`. A live run never falls back to fixtures.
- The UI shows a persistent **DEMO DATA** indicator in demo projects and labels evidence Live / Cached / Fixture.
- **Fixture provenance.** Until a Qloo credential is available, Qloo fixtures are hand-written in the
  harness result envelope (`fixture_origin: "hand_authored"`). Once a credential is available, replace them
  with sanitized captures (`"captured_live"`).
- The frontend **mock transport** (`NEXT_PUBLIC_API_MOCK=1`) serves `contracts/fixtures` for UI
  development only. It is not product demo mode, shows a **MOCK API** banner, and must never be enabled in production builds.

## 6. Runs

- Run-creating endpoints return `202` with `RunAccepted`. Poll `GET /runs/{id}` every 1.5 s for the
  first 30 s, then every 5 s. Stop polling at a terminal status: `completed`, `partial`, `failed`, `cancelled`.
- On `completed` or `partial`, `Run.result = {resource, ids, url}` points at the result. Discovery and
  rehearsal results are keyed by run id. Adaptations return a list of ids (also available via
  `GET /campaigns/{id}/adaptations?run_id=`). Evaluations return the evaluation id.
- `partial`: some stages succeeded. The result is available and its `limitations` name the missing parts.
- `failed`: `Run.error = {code, message, stage, retryable}`. `message` says what failed and whether anything was saved.
- Execution uses in-process background tasks on a single instance, which is not durable. On startup,
  any queued or running run becomes `failed` with `RUN_INTERRUPTED`.
- Discovery and rehearsal result GETs (keyed by run id) return `200` for a run of that type in any status. The
  `status` field mirrors the run; lists are empty and nullable sections are null while the run is queued or running,
  or when it failed. This lets a page reload mid-run. The evaluation resource exists once its run is `completed`
  or `partial`.
- At `completed`/`partial`, `progress.stage` is `"completed"` with `completed_steps = total_steps`. At `failed` it is
  the failing stage (the same as `Run.error.stage`).
- To list past discoveries, rehearsals, adaptation runs, or evaluations, use `GET /projects/{id}/runs?run_type=…` and follow `Run.result`.
- `progress.stage` values. Show `progress.message` to users.

| Run type | Stages, in order |
|---|---|
| `market_discovery` | `resolving_references`, `retrieving_affinities`, `normalizing_evidence`, `generating_brief` |
| `campaign_rehearsal` | `loading_context`, `generating_reactions`, `aggregating_results`, `analyzing_reactions` |
| `campaign_adaptation` | `loading_context`, `generating_adaptations`, `checking_constraints`, `reviewing_risks` |
| `campaign_evaluation` | `loading_candidates`, `assessing_candidates`, `scoring`, `recommending` |

## 7. Evidence classification

`evidence_type` says what produced a record; `claim_type` gives its epistemic status. The UI
label comes from the first matching row:

| UI label | Rule |
|---|---|
| Observed outcome | `evidence_type = observed_outcome` |
| Synthetic | `evidence_type = synthetic_response` or `claim_type = synthetic` |
| Calculated | `evidence_type = deterministic_calculation` |
| Unverified | `claim_type = hypothesis` |
| Model interpretation | `evidence_type = model_interpretation` |
| Source data | `evidence_type` in `qloo_source`, `provider_result`, `user_input` |

The retrieval badge comes from `retrieval_mode`: `live` → Live, `cached` → Cached (show `retrieved_at`),
`fixture` → Fixture, `user_input` → User input. `generated` shows no retrieval badge, because the evidence label
already says Calculated or Model interpretation.

There are no endpoints for dismissing a risk flag or for hand-picking individual evidence records or findings to pass to the
next stage. Stages take whole run ids, so the UI must not render those controls.

## 8. Scoring version `mvp-1`

**Audience aggregation** (deterministic, over synthetic ratings):

- Each synthetic reaction rates each requested dimension 1–5. For `cultural_risk`, 5 means the most perceived risk.
- `score = round((mean - 1) / 4 * 100, 1)`. `higher_is_better` is false only for `cultural_risk`.
- `spread` is the population standard deviation of the 1–5 ratings, rounded to 2 decimals.
- `disagreement = n >= 3 and (spread >= 1.0 or (share(rating <= 2) >= 0.25 and share(rating >= 4) >= 0.25))`.
- Segment scores use the same formula over that segment's reactions.

**Evaluation** (Loop):

- One model assesses every candidate (the original plus up to 3 adaptations) in a single run,
  with the same prompt and criteria. Each dimension gets an integer 0–100 with a rationale.
- `utility_d = score_d`, except `utility_cultural_risk = 100 - score_cultural_risk`.
  `overall = round(sum(weight_d * utility_d), 1)`. It is null if any dimension score is missing.
- Weights must sum to 1.0 within 0.001; otherwise the request fails with `422`. The default weights are
  clarity 0.30, brand_fidelity 0.25, cultural_relevance 0.30, cultural_risk 0.15.
- The best candidate is the adaptation with the highest `overall`. Ties go to the lower `cultural_risk`, then request order.
- Recommendation: the first matching rule wins.
  - R0 `R0_missing_scores`: any score missing for the original or the best candidate → `inconclusive`
  - R1 `R1_constraint_or_risk`: the best candidate has a constraint violation, a high-severity risk flag, or `cultural_risk >= 60` → `revise`
  - R2 `R2_no_improvement`: best `overall` < original `overall` → `revise`
  - R3 `R3_small_margin`: best − original < 5 → `validate`
  - R4 `R4_meets_review_threshold`: best `overall >= 70` and `cultural_risk < 40` → `accept` (for the next internal review, not proof of market success)
  - R5 `R5_default`: otherwise → `validate`

**Deterministic constraint checks** (case-insensitive):

- A protected term (brand kit plus request) that appears anywhere in the source content must appear
  verbatim in the adaptation. Otherwise it goes in `missing_protected_terms` and counts as a constraint violation.
- A prohibited term found in the adaptation goes in `prohibited_terms_found` and counts as a constraint violation.

**Confidence labels** (findings and brief findings). These are not probabilities:

- `moderate`: only for findings whose own `claim_type` is `observed` (brief) or `synthetic` (rehearsal). The finding
  must be backed by at least one Qloo evidence record with `claim_type = observed`. Rehearsal findings must also be
  supported by at least 50% of the reactions.
- `limited`: supported only by synthetic reactions or model interpretation, or the moderate rule's thresholds are not met.
  Findings with claim type `interpreted` or `hypothesis` are capped at `limited`.
- `insufficient`: fewer than 2 supporting reactions and no source evidence, or no support at all.
- There is no `high` label until observed real-world outcomes exist.

UI copy for the decision `inconclusive`: "Inconclusive — required scores are missing; rerun the evaluation."

### Rules

- **Brand Memory** is written only by people, through PUT. No model output is saved into it. Cultural DNA,
  Voice, Arena, Risk Radar, and market comparisons all read the current brand, and their results record which
  rules they applied. In demo projects, PUT returns 409 and the page is read-only.
- **Cultural DNA** grounds every item in discovery evidence. An item with no evidence is `hypothesis`,
  `insufficient`. Regenerating with `based_on_profile_id` creates the next version under the same `lineage_id`;
  earlier versions are never overwritten.
- **Market Expansion** runs the Atlas pipeline for each market. When the verified Qloo signals do not differ by
  market, `comparability.market_specific_signals` is false and the UI must not rank markets on those signals.
  A market with no data is `unavailable` and names the gap. Insight is never invented to fill a column.
- **Trend Watch** compares two saved snapshots deterministically, with no model call. The comparison is
  `comparable: false` (with notes) when the market, terms, or workflows differ. Implications are labeled `hypothesis`.
  Historical snapshots are never fabricated; with fewer than two snapshots, the UI shows an empty state.
- **Campaign Arena** gives every variant the study's segments, dimensions, and criteria. Scores aggregate synthetic
  ratings under `mvp-1`. The results carry the synthetic disclosure. Choosing a preferred variant is not approval.
- **Risk Radar** keeps `observation` (exact text, or a visible element) separate from `interpretation` (a model
  assessment, unless it came from a deterministic check). Applying an alternative creates a user-edit adaptation; it
  never edits the campaign in place.
- **Vision.** Images go only to a vision model that has been verified with real image inference. If none is
  configured or the call fails, `vision.status` is `unavailable` or `failed` with a message, and the text analysis still
  runs. An image is never sent to a text-only model. Visual observations are what is visible; cultural readings of them
  are interpretations.
- **Search and retrieval** use stored embeddings tagged with their model and dimensions. Embedding spaces are never
  mixed: a model change triggers re-embedding. `similarity` is not a probability. When embeddings are not configured,
  `status` is `unavailable`, and the API never returns lexical guesses dressed up as semantic results.
- **Evidence Graph** draws only persisted links. `provenance` names the field that establishes each edge.
- **Demo projects** run every v2 workflow on labeled fixtures for the seeded scenario:
  - Arena and risk scans of fixture content work.
  - Custom variants have null scores, with a limitation.
  - Uploaded images get `vision.status = "unavailable"`, with the message "Demo projects do not analyze uploads".
  - Search returns `unavailable`.
  - Non-JP columns in a market comparison are `unavailable`.
- **Uploads.** Images only: PNG, JPEG, or WebP up to `MAX_IMAGE_BYTES` (5 MB); other kinds return 422. The type is
  checked from the file's content (magic bytes), not only the filename or header. Stored names are server-generated.
  Files are served only through the authenticated `content` endpoint.
- **Capability routing** is configured with `EMBEDDING_*`, `VISION_*`, and `RERANK_*` (`backend/.env.example`).
  `/ready` reports the `capabilities`. Every model output records its provider and model in `StepTrace`.

### 14.2 Discovery confirmation

`DiscoveryCreate.confirmed_references` carries the person's choice among ambiguous candidates (`term`, `ref_id`,
`ref_kind`). The resolver uses a confirmed id instead of matching; every confirmed term must also be in
`reference_terms` (422 otherwise). Without a confirmation, ambiguous terms stay ambiguous and never flow downstream.

### 14.3 Population construction

- **Size** is 20–2,000 and is never silently reduced. The backend caps total work per run; when a requested size
  exceeds what the configured limits allow, the request is refused with 422 and the limit, not quietly shrunk.
- **Groups** (3–12) are archetypes built by a model from the study's discovery evidence (`discovery_run_id`, or the
  campaign's latest linked discovery). Each group cites `evidence_ids`; `interests` are Qloo tags/entities with a
  `weight` derived from evidence rank. Without evidence the population is built ungrounded (`grounded=false`) and every
  group is labeled a hypothesis.
- **Participants** are expanded deterministically from groups with the run seed: the same population id always has
  the same participants, so campaign versions are compared on identical people. Each participant gets a subset of
  the group's interests and seeded `traits` drawn only from `adoption_style`, `price_sensitivity`, `media_habit`, and
  `tone_preference`. No age, gender, ethnicity, religion, health, income, or other sensitive or demographic trait is
  invented; demographic signals appear only as cited aggregate evidence on a group, never on a person. A region is
  never assigned a single stereotype: groups within one region differ by interests and traits.
- `share` is a configuration choice (how participants were allocated), not market share or prevalence.

### 14.4 Interviews

- Every participant answers the core protocol about the actual campaign version: `first_impression`,
  `comprehension`, `relevance`, `appeal`, `confusion`, `trust`, `concerns`, `improvement`. `standard` depth adds one
  adaptive follow-up, `deep` adds two. Answers may be positive, mixed, neutral, negative, or confused; diversity is
  never forced or inflated.
- Interviews are batched (several participants per model call, each with its own profile) on the fast model. Each
  participant still gets its own answers, reaction, comprehension, themes, and concerns.
- A creative is shown only as verified vision observations (§13 Vision); a study never claims visual analysis when
  only text was processed.
- Aggregates are deterministic tallies over stored interviews: `rates = counts / denominator`, where `denominator` is
  completed interviews and `failed` is reported alongside. Theme counts tally the labels stored on each interview.
  Model text interprets tallies (`group_differences`, `next_actions`) and is labeled interpretation.

### 14.5 Background execution

- Runs use the existing engine with bounded concurrency, retries for retryable provider errors only, and a checkpoint
  after every interview batch (and every social round). Progress comes from persisted state.
- `POST /runs/{id}/cancel` stops at the next checkpoint and keeps saved work (status `cancelled`).
- `POST /runs/{id}/resume` continues an interrupted or failed run from its last checkpoint; completed batches are never
  redone (idempotent by batch index).
- The active-run cap per user still applies.

### 14.6 Social simulation

- Requires a completed or partial population study. Builds a seeded peer network: each participant links to `degree`
  peers by shared-interest similarity (mostly within the group, some across), documented in `network`.
- Each round, a seeded `active_share` of participants sees a feed of up to `feed_size` peer posts from its neighbors
  and chooses `post`, `comment`, `share`, or `ignore`, and states its current stance. Round 1 feeds come from peers'
  interview answers. At most 5 rounds.
- Stored per post: who, round, action, text, `previous_stance`, `stance`, the participant's stated `reason`, and
  `seen_post_ids` (the exact feed), so every influence claim and every stance change is traceable. `shifts` counts
  stance changes.
- Results are labeled "simulated social dynamics — illustrative, not a forecast". They never claim real virality,
  reach, or market behavior, and the disclosure notes that agents share one model.

### 14.7 Graph views

- Built only from stored records: no hardcoded nodes or invented counts. Every node and edge has a stable id; every
  weighted edge states `weight_definition`; every edge states `provenance`.
- **Graph B (landscape):** groups are nodes. `similar_to` edges use cosine similarity of the groups' interest-weight
  vectors over shared Qloo ids (defined in `weight_definition`), drawn only above a stated threshold. `shares_evidence`
  edges link groups that cite the same evidence. When no defensible similarity exists, only shared-evidence edges
  appear.
- **Graph C (reaction map):** campaign elements (headline, body, call to action, creative) link to the groups that
  mentioned them, to stored themes, to reaction categories, to cited evidence, and to recommendations.
- **Graph D (comparison):** campaign versions × groups × reaction distributions for population studies that share one
  `population_id` and interview depth; `consistent_population` / `consistent_protocol` say whether that holds.
- **Diffusion:** group-level influence flows plus a bounded participant/post subgraph for one round.
- Large studies return a bounded, relevant subgraph (`limit`) with `truncated=true` and a limitation; clients expand
  through the paginated list endpoints.

### 14.8 Participant memory and interrogation

- A participant's **state** in a study is its latest stance (interview reaction, then any later social-round stance)
  with its source. Its **memories** are built only from stored records — its interview answers, the posts it saw,
  its own posts, and its earlier follow-up answers — most recent first, at most 50. Nothing is remembered that was not
  stored.
- `GET /population-studies/{id}/participants/{participant_id}` returns the profile, state, and memories.
- `POST .../participants/{participant_id}/questions` asks one participant a follow-up: one bounded model call, in
  character, using the profile and a bounded memory window. The answer lists `memory_refs` and is stored, so it
  becomes a memory itself. `POST .../groups/{group_id}/questions` asks a seeded sample (3–10) of one group in a single
  batched call; the tally covers the sample only and `sample_note` says so.
- Answers are synthetic and labeled; they are never presented as a real person's opinion. Demo projects return a
  labeled fixture answer that quotes the participant's stored interview, with no provider call.

### 14.9 Out of scope

Speech-to-text, image generation, and video generation are intentionally excluded (D-048): no endpoints, settings, or
UI exist for them. Image upload and vision analysis of campaign creatives (§13) remain in scope.

### 14.10 Demo projects

Demo projects run population studies and social simulations on labeled fixtures for the seeded scenario
(Northstar, Japan): fixture groups and deterministic fixture answers, no provider calls, `mode = "demo"` on every
population, study, and simulation, and `is_demo` on every graph node. Sizes above the demo cap (120) are refused with
409 and the reason.
