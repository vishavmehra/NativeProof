# Walkthrough script and shot list

One real session on https://nativeproof.vercel.app (October 29, 2026), live mode only, recorded with the judging account, with the architecture diagrams narrated beside the features they explain. Each shot lists what is on screen, the voiceover, the length of the real recording, and the playback speed used in the video. The voiceover is synthetic (Microsoft Edge text to speech, `en-US-AndrewMultilingualNeural`).

## 1. Nativeproof

*A real session on nativeproof.vercel.app with live Qloo data and live models*

- **On screen:** title card
- **Voiceover:** This is Nativeproof, a research workspace for testing how a campaign may be received in another culture before money is spent on it. A team brings a product, a campaign and a target market. Nativeproof finds cultural signals in Qloo's affinity data, rehearses the campaign with a labeled synthetic audience, flags cultural risks, adapts the copy, compares the versions with a fixed scoring rule, and assembles a report in which every claim points back to its source. Everything in this video was recorded on the deployed app on October twenty-ninth, with live Qloo data and live language models. The synthetic participants are generated by AI. They are not real people, and the app says so wherever they appear.

## 2. How it is built

*Architecture, deployment and sign-in*

- **On screen:** diagram `diagrams/png/01-system-architecture.png`
- **Voiceover:** First, how the system is built. The web app is Next.js, and it talks to a FastAPI service over HTTPS with a bearer token. Its API types are generated from the service's OpenAPI contract, so the two sides cannot drift apart silently. Inside the API, routes check ownership, a run engine executes long jobs in the background, and each job is a LangGraph workflow with four named stages. Model calls go through one gateway with strict output schemas, while scoring, tallies and rule checks are plain deterministic code. Qloo is reached only from the server, and everything is stored in PostgreSQL.

## 3. Deployment

- **On screen:** diagram `diagrams/png/02-deployment.png`
- **Voiceover:** In production, the web app runs on Vercel, the API runs on a free Render web service in Singapore, and Supabase provides sign-in, the PostgreSQL database and private file storage. An uptime monitor calls the health endpoint every five minutes, so the free service stays awake. Provider keys exist only as server environment variables. The browser never sees a Qloo key, a model key or a database password.

## 5. Authentication

- **On screen:** diagram `diagrams/png/03-authentication.png`
- **Voiceover:** All three sign-in paths end in one Supabase session. The API does not trust the browser: it verifies every token itself against Supabase's public signing keys, checks the expiry, audience and issuer, and uses the token's subject as the user id. Every project belongs to one owner, and a request for another user's data gets a not found response.

## 7. The research workflow

*From a project to an evidence-backed report*

- **On screen:** diagram `diagrams/png/04-campaign-lifecycle.png`

## 8. Qloo evidence pipeline

- **On screen:** diagram `diagrams/png/05-qloo-evidence-pipeline.png`
- **Voiceover:** Here is how a Qloo result becomes evidence. Inputs are validated, and terms that look like an email address or a phone number are refused before anything leaves the server. Only an allowlist of workflows can run. Each response is normalized into evidence records that keep the retrieval mode, the retrieval time and hashes of the request and response, and live results are cached for a limited time. When a term matches several candidates, nothing is chosen automatically.

## 11. How a synthetic population is built

*Groups from evidence, participants from groups, interviews in batches*

- **On screen:** diagram `diagrams/png/07-population-generation.png`
- **Voiceover:** A population study works in three steps. A model proposes audience groups, and each group must cite the Qloo evidence it is built from. Participants are then sampled into those groups with a fixed random seed, so the same population can be interviewed again later. Interviews run in batches, and every completed batch is saved as a checkpoint before the next one starts.

## 15. How the social simulation works

*Rounds, feeds, stances and traceable influence*

- **On screen:** diagram `diagrams/png/09-social-simulation.png`
- **Voiceover:** The social simulation runs in rounds. In each round, a share of participants reads a feed of peer posts and interviews, chosen with a fixed seed, and then posts, comments, shares or ignores. Each action stores the stance before and after, the stated reason, and the exact feed items the participant saw. That is what makes every claimed influence traceable, and each completed round is a checkpoint.

## 20. The model gateway

*One place for routing, validation, retries and usage*

- **On screen:** diagram `diagrams/png/06-model-gateway.png`
- **Voiceover:** Every model call goes through one gateway. Each task has a configured model and a minimum capability, and outputs must match a strict schema. Invalid output gets a bounded repair attempt, provider errors get bounded retries, and a fallback provider is used only when it is enabled and capable. Usage and latency are recorded per stage, which is how the report can list the model and prompt version behind every step.

## 25. Runs, checkpoints and recovery

*What happens when a run is cancelled or the server restarts*

- **On screen:** diagram `diagrams/png/12-runs-checkpoints-testing.png`
- **Voiceover:** Long work runs in the background with a clear lifecycle: queued, running, then completed, partial, failed or cancelled. Population studies and social simulations save a checkpoint after every batch or round. Cancelling stops at the next checkpoint and keeps the finished work. If the server restarts, a startup sweep marks unfinished runs as interrupted, and runs with a checkpoint can be resumed from where they stopped.
